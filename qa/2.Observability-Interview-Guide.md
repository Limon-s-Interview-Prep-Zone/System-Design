# Senior System Design Interview: Observability & Distributed Telemetry

> **Interviewer Prompt:**  
> *"Design an enterprise-grade observability architecture for a large-scale, high-throughput microservices platform handling 50,000 requests per second across multiple regions. Walk me through the Three Pillars (Metrics, Logs, Traces), correlation strategies, capacity estimations, sampling trade-offs, and resilience integration."*

---

## 1. Stage 1: Clarifying Questions & Scope

### Functional Scope
- **Telemetry Pillars**: Ingestion, processing, storage, querying, and correlation across **Metrics, Logs, and Traces (M.E.L.T)**.
- **Root-Cause Analysis (RCA)**: Jump seamlessly from a 5xx latency spike on a Grafana chart to the exact distributed trace span, and down to the specific structured log line with zero manual searching.
- **Actionability & Alerting**: Multi-window, multi-burn-rate alerting tied directly to SLOs/SLIs (Service Level Objectives/Indicators) without alert fatigue.

### Non-Functional Requirements & Constraints
- **Throughput Scale**: $50,000\text{ RPS}$ average, with $3\times$ peak traffic ($150,000\text{ RPS}$).
- **Target SLO**: $99.99\%$ availability for business services; observability agent overhead must consume $< 2\%$ CPU and $< 100\text{ MB}$ memory per application pod.
- **Latency Budget for Telemetry**: Async non-blocking ingestion; application request latency penalty must be $< 1.5\text{ ms}$.
- **Data Retention & Tiering**:
  - Metrics: 90 days downsampled (15s raw $\rightarrow$ 5m rollups $\rightarrow$ 1h rollups).
  - Traces: 14 days (100% of errors and p99.9 outliers; head/tail-sampled 1% of normal 200 OKs).
  - Logs: Hot tier on SSD for 7 days, cold tier on object storage (S3/Azure Blob) for 90 days (compliance).
- **Compliance & Privacy**: PII redaction (masking credit cards, emails, tokens) must happen at the local node agent before leaving the network boundary.

## 2. Stage 2: Back-of-the-Envelope Capacity Estimations

Let’s calculate the telemetry volume, network egress, and disk storage requirements for **50,000 RPS** (Average) and **150,000 RPS** (Peak).

### 1. Metrics Ingestion & TSDB Storage
- **Application Services**: 100 distinct microservices, running an average of 5 pods each = 500 active pods.
- **Metrics per Pod**: 200 time-series metrics (HTTP rates, histograms, runtime GC, thread pool, DB connections).
- **Active Time Series**: $500\text{ pods} \times 200 = 100,000\text{ unique metric series}$.
- **Scrape Interval**: Every $15\text{ seconds}$ ($\approx 4\text{ scrapes/min}$).
- **Samples per Second**:
  $$\frac{100,000 \text{ series}}{15\text{ s}} \approx 6,666\text{ metric samples/sec}$$
- **TSDB Compression**: Gorilla compression averages $\approx 1.5\text{ bytes per sample}$.
- **Daily Metrics Ingress**:
  $$6,666 \times 1.5\text{ bytes} \times 86,400\text{ s} \approx 864\text{ MB/day} \approx 0.86\text{ GB/day}$$
- **Conclusion**: Metrics volume is exceptionally lightweight if cardinality is kept under control.

### 2. Structured Log Ingestion & Storage
- **Log Rate**: Average 3 structured log statements per incoming HTTP request (Request received, DB query summary, Response sent).
- **Daily Requests**: $50,000\text{ RPS} \times 86,400\text{ s} = 4,320,000,000\text{ requests/day}$ ($4.32\text{ Billion}$).
- **Log Events/Day**: $4.32\text{B} \times 3 \approx 13\text{ Billion log lines/day}$.
- **Average JSON Log Size**: $400\text{ bytes}$ (timestamp, correlation ID, service name, environment, message, parameters).
- **Raw Daily Storage**:
  $$13,000,000,000 \times 400\text{ bytes} \approx 5.2\text{ TB/day (uncompressed)}$$
- **Compressed Storage** ($4\times$ zstandard compression in storage engine):
  $$\frac{5.2\text{ TB}}{4} \approx 1.3\text{ TB/day}$$
- **7-Day Hot Storage (SSD)**: $1.3\text{ TB} \times 7 \approx \mathbf{9.1\text{ TB}}$.
- **90-Day Cold Archive (Object Storage)**: $1.3\text{ TB} \times 90 \approx \mathbf{117\text{ TB}}$.

### 3. Distributed Trace Spans & Sampling Budget
- **Spans per Request**: 1 upstream gateway + 2 downstream service hops + 2 database/cache calls = 5 spans per trace.
- **Total Spans Generated**: $50,000\text{ RPS} \times 5 = 250,000\text{ spans/sec}$.
- **Span Size**: $500\text{ bytes}$ (TraceId, SpanId, ParentSpanId, Baggage, HTTP metadata).
- **Unsampled Volume**:
  $$250,000 \times 500\text{ bytes} = 125\text{ MB/s} \approx 10.8\text{ TB/day}$$
- **Applying Tail-Based Sampling**:
  - Sample $100\%$ of requests returning HTTP $\ge 400$ or latency $> 500\text{ ms}$ (assume $2\%$ of traffic).
  - Sample $1\%$ of normal healthy requests ($200\text{ OK}$).
  - Effective Sampling Rate: $2\% + (98\% \times 0.01) = 2.98\% \approx 3\%$.
- **Sampled Daily Storage**:
  $$10.8\text{ TB} \times 0.03 \approx \mathbf{324\text{ GB/day}}$$
- **14-Day Trace Retention**: $324\text{ GB} \times 14 \approx \mathbf{4.5\text{ TB}}$.

## 3. Stage 3: High-Level Observability Architecture

The following diagram illustrates how telemetry flows from application pods through the local OpenTelemetry Collector DaemonSet, central gateways, dedicated storage engines, and into unified dashboards and paging alerts.

![Observability Architecture](../images/observability-architecture.svg)

### Architectural Flow Milestones:
1. **In-Process Instrumentation**: ASP.NET Core applications use OpenTelemetry .NET SDK with `System.Diagnostics.Activity` and `System.Diagnostics.Metrics`. Spans, metrics, and JSON logs are exported out-of-process via OTLP/gRPC to a local localhost sidecar or node DaemonSet.
2. **Node Agent (DaemonSet)**: Performs PII scrubbing, memory limiting, and local batching. Decouples app execution from network issues in the monitoring backend.
3. **Cluster Gateway**: Manages tail-based sampling decisions, drops high-cardinality rogue tags, and balances load across backend storage engines.
4. **Specialized Storage Engines**:
   - Time-series TSDB (Prometheus / VictoriaMetrics / Mimir) for metrics.
   - Columnar / Index-free storage (Grafana Loki) or Search cluster (Elasticsearch / OpenSearch) for logs.
   - Distributed object storage (Grafana Tempo / Jaeger) for traces.
5. **Unified Correlation Plane**: Grafana links Metrics $\rightarrow$ Traces (via Exemplars) $\rightarrow$ Logs (via TraceId).

## 4. Stage 4: Deep Dive — Observability Levers (.NET Enterprise Standards)

### Lever 1: Distributed Tracing with W3C TraceContext & Activity API

#### Overview & How it Works
Distributed tracing follows a request across multiple network boundaries. It assigns a globally unique `TraceId` (32-hex characters) and a local segment `SpanId` (16-hex characters). The W3C `traceparent` header format (`00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`) is injected into outgoing HTTP/gRPC/Kafka headers.

#### Benefits
- Identifies critical path latency bottlenecks across complex microservice graphs.
- Pinpoints exactly which downstream service, database query, or queue caused a timeout.

#### Drawbacks & Trade-offs
- Network serialization and memory overhead if spans are over-instrumented.
- High storage cost unless intelligent sampling is enforced.

#### Target Technology & NuGet Packages for .NET / C#
- `OpenTelemetry.Extensions.Hosting`
- `OpenTelemetry.Instrumentation.AspNetCore`
- `OpenTelemetry.Instrumentation.Http`
- `OpenTelemetry.Instrumentation.EntityFrameworkCore`
- `OpenTelemetry.Exporter.OpenTelemetryProtocol` (OTLP)

#### Minimal Code Example
```csharp
// Program.cs - Zero-overhead native OpenTelemetry setup
using OpenTelemetry.Resources;
using OpenTelemetry.Trace;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource.AddService("OrderService", serviceVersion: "1.2.0"))
    .WithTracing(tracing =>
    {
        tracing
            .AddAspNetCoreInstrumentation(opts =>
            {
                opts.RecordException = true;
                opts.Filter = httpContext => !httpContext.Request.Path.StartsWithSegments("/healthz");
            })
            .AddHttpClientInstrumentation()
            .AddEntityFrameworkCoreInstrumentation(opts => opts.SetDbStatementForText = true)
            .AddSource("Enterprise.OrderProcessing") // Custom business ActivitySource
            .AddOtlpExporter(opts =>
            {
                opts.Endpoint = new Uri("http://otel-collector.monitoring:4317"); // Local DaemonSet
                opts.Protocol = OpenTelemetry.Exporter.OtlpExportProtocol.Grpc;
            });
    });
```

### Lever 2: High-Performance Structured Logging & Trace Correlation

#### Overview & How it Works
Plain text logs (`Console.WriteLine`) are unsearchable at scale. Structured logging writes JSON key-value pairs. Crucially, the current `TraceId` and `SpanId` must be automatically injected into every single log context so that filtering by a Trace ID in Loki/Elasticsearch returns every single log emitted across 10 microservices for that specific user request.

#### Benefits
- Instant needle-in-a-haystack debugging across distributed nodes.
- High machine-readability for automated indexing and anomaly detection.

#### Drawbacks & Trade-offs
- JSON serialization consumes CPU cycles and increases payload size.
- String interpolation (`$"Processing order {id}"`) causes GC allocations. Must use **Source Generators** (`[LoggerMessage]`) or structured templates.

#### Target Technology & NuGet Packages for .NET / C#
- `Serilog.AspNetCore`
- `Serilog.Enrichers.Span`
- `Serilog.Sinks.OpenTelemetry` or `Serilog.Sinks.Elasticsearch`

#### Minimal Code Example
```csharp
// Program.cs - Serilog with Automatic TraceId Correlation & High-Performance Logging
using Serilog;
using Serilog.Enrichers.Span;

Log.Logger = new LoggerConfiguration()
    .Enrich.FromLogContext()
    .Enrich.WithSpan() // Automatically attaches TraceId and SpanId from Activity.Current
    .WriteTo.Console(new Serilog.Formatting.Json.JsonFormatter())
    .WriteTo.OpenTelemetry(opts =>
    {
        opts.Endpoint = "http://otel-collector.monitoring:4317";
        opts.Protocol = Serilog.Sinks.OpenTelemetry.OtlpProtocol.Grpc;
    })
    .CreateLogger();

builder.Host.UseSerilog();

// High-Performance Zero-Allocation Structured Log using C# Source Generator
public static partial class OrderLogExtensions
{
    [LoggerMessage(
        EventId = 1001,
        Level = LogLevel.Information,
        Message = "Order {OrderId} successfully placed for customer {CustomerId} with total {Amount}")]
    public static partial void LogOrderPlaced(
        this ILogger logger, string orderId, string customerId, decimal amount);
}
```

### Lever 3: Structured Metrics, Histograms & Cardinality Protection

#### Overview & How it Works
Metrics aggregate numerical observations over time (Counters, Gauges, Histograms). A Counter records counts (e.g., total requests), while a Histogram records values into exponential buckets to calculate p50, p95, and p99 percentiles without storing raw events.

#### Benefits
- O(1) storage cost relative to request volume. A million requests compress into a few numerical counter buckets.
- Ideal for fast, continuous alerting and dashboard monitoring.

#### Drawbacks & Trade-offs
- **The High Cardinality Trap**: Adding unique identifiers (e.g., `UserId`, `OrderId`, email) as label dimensions causes an exponential explosion of time-series in memory, crashing Prometheus.

#### Target Technology & NuGet Packages for .NET / C#
- `System.Diagnostics.Metrics` (.NET native)
- `OpenTelemetry.Extensions.Hosting`
- `OpenTelemetry.Instrumentation.Runtime`
- `OpenTelemetry.Instrumentation.Process`

#### Minimal Code Example
```csharp
// Business Metrics with Native System.Diagnostics.Metrics
using System.Diagnostics.Metrics;

public sealed class OrderMetrics
{
    private static readonly Meter EnterpriseMeter = new("Enterprise.OrderService", "1.0.0");
    private readonly Counter<long> _orderCounter;
    private readonly Histogram<double> _orderProcessingDuration;

    public OrderMetrics()
    {
        _orderCounter = EnterpriseMeter.CreateCounter<long>(
            name: "orders_placed_total",
            unit: "orders",
            description: "Total count of successfully placed orders");

        _orderProcessingDuration = EnterpriseMeter.CreateHistogram<double>(
            name: "order_processing_duration_seconds",
            unit: "s",
            description: "Time taken to process checkout pipeline");
    }

    public void RecordOrder(string orderType, string paymentMethod, double durationSec)
    {
        // Safe: Low cardinality dimensions (orderType, paymentMethod)
        // UNSAFE ANTI-PATTERN: Never add OrderId or UserId as a Tag!
        var tags = new TagList
        {
            { "order_type", orderType },
            { "payment_method", paymentMethod }
        };

        _orderCounter.Add(1, tags);
        _orderProcessingDuration.Record(durationSec, tags);
    }
}
```

### Lever 4: Synthetic Probing & Blackbox Health Verification

#### Overview & How it Works
Internal metrics only report errors on endpoints users actually hit. If DNS or the load balancer breaks, internal metrics report zero errors (silent failure). Synthetic monitoring probes public endpoints from external vantage points at scheduled intervals.

#### Benefits
- Catches edge-routing, SSL certificate expiration, and DNS failures before customers complain.
- Independent verification of uptime SLAs.

#### Drawbacks & Trade-offs
- Adds synthetic traffic that must be excluded from business analytics.

#### Target Technology & NuGet Packages for .NET / C#
- `AspNetCore.HealthChecks.UI`
- `AspNetCore.HealthChecks.Npgsql` / `AspNetCore.HealthChecks.Redis`
- External probes: Prometheus Blackbox Exporter or Datadog Synthetics.

#### Minimal Code Example
```csharp
// Program.cs - Deep Health Checks with Readiness & Liveness
builder.Services.AddHealthChecks()
    .AddNpgSql(builder.Configuration.GetConnectionString("PostgresDb")!, name: "postgres_db")
    .AddRedis(builder.Configuration.GetConnectionString("RedisCache")!, name: "redis_cache");

app.MapHealthChecks("/healthz/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

app.MapHealthChecks("/healthz/live", new HealthCheckOptions
{
    Predicate = _ => false // Just verifies the Kestrel process is responding
});
```

## 5. Stage 5: Reliability, Incident Drills & Alerting Strategy

### Drill 1: The Multi-Window Multi-Burn-Rate Alerting Strategy (Google SRE)
- **The Problem**: A static threshold alert (e.g., `Error Rate > 1%`) creates either massive alert fatigue during tiny 10-second hiccups, or fails to catch slow, catastrophic 6-hour degradations.
- **The Solution**: Alert on **SLO Error Budget Burn Rate**.
  - If a system has a $99.9\%$ SLO, it has a $0.1\%$ error budget over 30 days.
  - A **$14.4\times$ burn rate** consumes $2\%$ of the monthly budget in 1 hour $\rightarrow$ **Critical Page (PagerDuty)**.
  - A **$6\times$ burn rate** consumes $5\%$ of the budget in 6 hours $\rightarrow$ **Ticket/Slack notification**.

```yaml
# Prometheus Alertmanager Rule
groups:
  - name: order_service_slo_alerts
    rules:
      - alert: ErrorBudgetBurnRateCritical
        expr: (
            sum(rate(http_requests_total{status=~"5.."}[1h])) 
            / 
            sum(rate(http_requests_total[1h]))
          ) > (14.4 * 0.001)
        for: 2m
        labels:
          severity: page
        annotations:
          summary: "1-hour burn rate exceeds 14.4x (2% error budget consumed in 1h)"
          runbook_url: "https://wiki.enterprise.com/runbooks/order-service-error-burn"
```

### Drill 2: High Cardinality Outage & Memory Exhaustion Mitigation
- **The Scenario**: A developer instruments `http_requests_total` and accidentally tags each sample with `user_id` or `credit_card_number`. Within 15 minutes, Prometheus RAM skyrockets from 8 GB to 64 GB and triggers an Out-Of-Memory (OOM) crash loop.
- **The Production Fix**:
  1. **Collector Filter Rules**: Implement metric relabeling in OpenTelemetry Collector to strip unauthorized label keys (`user_id`, `email`, `guid`).
  2. **Collector Memory Limiter**: Configure `memory_limiter` processor in the OTel collector to drop telemetry when buffer memory reaches $80\%$, rather than crashing the node.
  3. **Linting & Code Analyzers**: Integrate Roslyn analyzers in CI/CD to prevent passing high-cardinality strings to `TagList`.

### Drill 3: Head-Based vs. Tail-Based Trace Sampling
- **Head-Based Sampling**: The sampling decision is made at the initial entry gateway *before* the request completes (e.g., random 5% coin toss).
  - *Failure Mode*: If an error or high-latency bottleneck occurs in the remaining 95% of traffic, the trace is completely missing.
- **Tail-Based Sampling**: The collector buffers all spans of a trace in memory until the request finishes.
  - *Production Strategy*:
    - If `http.status_code >= 400` $\rightarrow$ Keep $100\%$.
    - If `duration >= 500ms` (p99 latency) $\rightarrow$ Keep $100\%$.
    - If normal 200 OK $\rightarrow$ Keep $1\%$.
  - Saves $97\%$ of network and storage cost while guaranteeing zero visibility loss for production outages.

## 7. Most Frequently Asked Interview Questions & Comprehensive Answers

### Q1: "Metrics vs. Logs vs. Traces — when do you choose which, and what are their fundamental economic trade-offs?"
- **Model Answer**:
  - **Metrics** answer *"Is the system healthy, and where is the aggregate anomaly?"*. They are numerical time-series with $O(1)$ storage cost relative to traffic volume (100,000 requests aggregate into the same fixed counter buckets). They are ideal for real-time dashboards and triggering alerts.
  - **Traces** answer *"Where is the critical path latency bottleneck across 15 microservices?"*. They model the request lifecycle as a Directed Acyclic Graph (DAG) of parent-child spans. Their economic cost is $O(N)$ with request volume, necessitating tail-based sampling in production to control costs.
  - **Logs** answer *"Why did a specific line of code fail under those exact parameters?"*. They provide contextual textual truth (stack traces, payload dumps). However, logs are the **most expensive** telemetry tier ($O(N)$ volume, expensive disk indexing, and massive JSON serialization overhead).
  - **Senior Synthesis**: Start investigation on Metrics (alert triggers) $\rightarrow$ isolate the slow component via Distributed Tracing $\rightarrow$ inspect the exact error root cause in the correlated Structured Log line.

### Q2: "Push vs. Pull telemetry collection: Why does Prometheus use Pull, while OpenTelemetry / CloudWatch use Push? Which is superior?"
- **Model Answer**:
  - **Pull (Prometheus)**:
    - *Mechanism*: Prometheus server queries `/metrics` HTTP endpoints on application instances discovered via Kubernetes API / Consul.
    - *Pros*: Centralized control of scrape intervals; easy detection of dead instances (if pull fails $\rightarrow$ instance is down); prevents monitoring server from being overwhelmed by runaway clients.
    - *Cons*: Requires network ingress access into the cluster; difficult across firewalls, serverless (AWS Lambda), or ephemeral batch jobs without an intermediary Pushgateway.
  - **Push (OTel / StatsD / CloudWatch)**:
    - *Mechanism*: Application actively sends telemetry batches over OTLP/gRPC to a collector or endpoint.
    - *Pros*: Natural fit for serverless/short-lived lambdas, edge clients, and cross-VPC architectures behind strict egress-only firewalls.
    - *Cons*: Risk of overwhelming collector backends during traffic bursts (requires local client-side buffering and drop policies); difficult to detect dead instances versus silent instances.
  - **The Staff-Level Verdict**: The modern industry standard is **Hybrid Push-Pull**: Applications *Push* over localhost OTLP/gRPC to an OpenTelemetry Collector DaemonSet running on the same host/VM, which then buffers, batches, and exposes or *Pushes* out to Prometheus, Tempo, or cloud backends.

### Q3: "How does Distributed Context Propagation actually work across HTTP, gRPC, and Asynchronous Message Brokers like Kafka?"
- **Model Answer**:
  - When an incoming request enters the API Gateway, the gateway checks for standard headers. If absent, it creates a new **W3C TraceContext** consisting of:
    1. `traceparent`: `00-{trace-id}-{parent-id}-{trace-flags}` (e.g., `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`).
    2. `tracestate`: Vendor-specific routing opaque pairs.
    3. `baggage`: Optional key-value metadata propagated across hops (e.g., `tenant-id=enterprise-42`).
  - **HTTP/gRPC**: Injected into HTTP headers or gRPC metadata by client interceptors (`HttpClientHandler`).
  - **Asynchronous Message Brokers (Kafka/RabbitMQ)**:
    - The message publisher extracts the active `Activity.Current` and serializes the `traceparent` into **Kafka Record Headers** (byte array).
    - The consumer worker reads the record header *before* processing the message, calls `ActivitySource.StartActivity("ProcessOrder", ActivityKind.Consumer, parentContext)`, and restores the distributed trace parent link.
  - This ensures that asynchronous event-driven pipelines maintain an unbroken, end-to-end distributed trace graph.

## 8. High-Pressure Follow-Up Questions & Production Counter-Answers

### Follow-Up 1: "What happens when the Observability backend (Elasticsearch or Kafka) crashes? How do you prevent telemetry from bringing down your revenue-generating production services?"
- **Interviewer's Trap**: Checking if your logging framework can block app threads or crash pods with OOM.
- **Battle-Tested Answer**:
  1. **Strict Asynchronous Non-Blocking Egress**: Application logs and traces must never write synchronously over network sockets. Serilog and OpenTelemetry write into bounded in-memory circular buffers (e.g., `Channel<T>` with `BoundedChannelFullMode.DropOldest`).
  2. **Fail-Open Drop Policy**: Telemetry is non-critical path data. If the local queue fills up, **drop telemetry immediately** and increment a local dropped-packet counter. Never block business threads.
  3. **Decoupled Local DaemonSet**: Applications send to `localhost:4317` (in-pod or node DaemonSet). If Elasticsearch crashes, the node OTel collector absorbs the spike with local disk-backed buffers (`file_storage` extension), rate-limits outbound retries, and shields the core microservices.

### Follow-Up 2: "How do you detect 'Silent Partial Failures' where HTTP endpoints return 200 OK, but business logic is fundamentally broken?"
- **Interviewer's Trap**: Checking whether you blindly rely on HTTP 500 error rates.
- **Battle-Tested Answer**:
  1. **Semantic Business Metrics**: Instrument domain invariants (e.g., `order_completion_rate`, `zero_search_results_ratio`, `payment_gateway_success_ratio`). If HTTP traffic is 10,000 RPS 200 OK, but `orders_placed_total` drops to 0, an anomaly alert fires.
  2. **Synthetic Canaries (Synthetics)**: Deploy scheduled headless browser bots (Playwright/Puppeteer) executing full synthetic user journeys (Search $\rightarrow$ Add to Cart $\rightarrow$ Mock Checkout) every 60 seconds from external regions.
  3. **Payload Contract Validation**: Log warnings and emit counter anomalies when response payloads violate size or schema expectations (e.g., API returning 200 OK with `{ "items": [] }` for high-volume catalog queries).

### Follow-Up 3: "How do you solve PII / GDPR compliance leaks in logs and traces without crippling developer productivity?"
- **Interviewer's Trap**: Asking if developers should just 'be careful' not to log passwords or credit cards.
- **Battle-Tested Answer**:
  1. **Edge PII Redaction in OTel Collector**: Use the OpenTelemetry Collector `transform` / `redaction` processor with regex patterns at the cluster boundary to mask SSNs, credit cards (Luhn check), and Authorization Bearer tokens into `***REDACTED***`.
  2. **Compile-Time Structural Guardrails in .NET**:
     - Leverage C# Source Generated `[LoggerMessage]` where log parameters are explicitly strongly typed.
     - Apply custom `[PersonalData]` attributes on domain DTOs and customize the JSON serializer / Serilog destructuring policy to automatically redact decorated properties.
  3. **Role-Based Field Masking in Log Storage**: Configure Elasticsearch/Loki field-level security (FLS) to hide customer email and IP fields from standard developers while keeping them accessible to authorized Security/Compliance auditors.
